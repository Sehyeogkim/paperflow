You judge, for THIS project, how strongly each candidate requirement key is expected —
turning clustered literature observations into a project-specific requirement schema.

You are given:
- the project's study archetype and research state (objective, design, methods, outcomes, claims),
- the set of canonical clusters (key, category, aliases, applicable_to, and the papers that
  reported each — with each paper's content level).

For EACH cluster, decide:
- `applicability`: { required_when: [...claim/study conditions...],
                     not_applicable_when: [...] } — when this requirement does/doesn't apply.
- `applicable_papers`: how many of the source papers this requirement actually applies to
  (the prevalence denominator). Never larger than the number of distinct source papers.
- `requirement_level`, exactly one of:
    mandatory          — a journal/reporting standard requires it, OR it is logically
                         necessary for the project's central claim to hold.
    strongly_expected  — a majority of similar, applicable papers report it AND it directly
                         affects the credibility of this project's claims; a reviewer would
                         likely demand it.
    common             — frequently reported but not essential to THIS project's core claim.
    optional           — only used in specific designs/implementations.
    unsupported        — weak evidence, or it leans on abstract-only inference; DO NOT use
                         this to drive a question.
- `reason`: one sentence, grounded in the project's claim and the literature pattern.

Rules:
- Be honest about content level: a key supported only by abstract_only papers cannot be
  "mandatory" on detailed-method grounds — downgrade to common/unsupported unless logic or a
  guideline makes it mandatory.
- Do NOT invent keys that are not in the clusters.
- Tie each requirement to the project's actual claims (e.g. a "peak stress increased" claim
  makes mesh_independence strongly_expected; "A more important than B" makes a sensitivity /
  uncertainty requirement strongly_expected).

Return ONLY JSON:
{
  "study_archetype": "...",
  "requirements": [
    {
      "key": "...",
      "applicability": {"required_when": ["..."], "not_applicable_when": ["..."]},
      "applicable_papers": 0,
      "requirement_level": "mandatory|strongly_expected|common|optional|unsupported",
      "reason": "..."
    }
  ]
}
